# The documentation site

The user pages and an API reference generated from the docstrings build into one website,
which GitHub Pages serves at <https://chipkent.github.io/deephaven-massive/> once the owner
turns publishing on (see the last section). Until then, CI builds the site on every pull
request that changes its sources, and nothing is published.

## What the site holds

[Zensical](https://zensical.org) builds the site from `zensical.toml`, with the API reference
plugin [mkdocstrings](https://mkdocstrings.github.io/python/). Both are in the `site`
dependency group, which a plain `uv sync` does not install.

| Section | Source |
|---|---|
| Home | `README.md` |
| Troubleshooting | `docs/troubleshooting.md` |
| Configuration | `docs/configuration.md` |
| Datasets | `docs/datasets/`, generated by `scripts/render_reference.py` |
| API reference | the docstrings, through the `:::` directives of the pages under `docs/api/` |
| Contributing | `CONTRIBUTING.md` |

The site reads the pages where they are. `zensical.toml` makes the repository root the docs
directory and lists the pages to publish in `exclude_docs`, so every relative link works the
same on GitHub and on the site, and no page is copied or rewritten. A link from a published
page to a page the site leaves out, such as one under `docs/dev/`, is a full GitHub URL.
Docstrings cite pages by full GitHub URL too, so their links work from an IDE or the console
whether or not the site is live.

The pages are written for GitHub, and the site renders them the same way: its Markdown
extensions and heading anchors follow GitHub's. Two differences remain, which no page has
today: a list needs a blank line before it, and a nested list needs four spaces of indent.

The API reference reads the source without importing it, so it needs no Deephaven server.

- **Namespaces.** Each dataset method lives on a private namespace class, so its page heads the
  class's section with the path users type, such as `m.stocks.financials`.
- **Examples.** The docstrings mark examples with reST's `::`. The griffe extension
  `scripts/site_literal_blocks.py` turns each marked block into a fenced code block on the
  site; the source keeps the `::`.
- **Coverage.** `tests/test_docs.py` checks that every public name and every namespace has a
  directive, and that every page under `docs/api/` is in the navigation. A new public name or
  namespace needs a directive.

The anchors and the search index of the API reference still name the private classes, as in
`#deephaven_massive._namespaces.stocks._Stocks.bars`.

## Build it

```bash
UV_PROJECT_ENVIRONMENT=.venv-site scripts/build_site.sh --only-group site
UV_PROJECT_ENVIRONMENT=.venv-site uv run --only-group site zensical serve   # preview at localhost:8000
```

The site goes to `site/`, which git ignores. It gets an environment of its own, `.venv-site`,
because syncing the project's `.venv` to only the `site` group would remove the dev tools.

`scripts/build_site.sh` fails on:

- a broken link or anchor in a published page (Zensical's strict mode);
- any warning about a docstring, such as an `Args` entry for a parameter that does not exist,
  which Zensical's strict mode lets through;
- a `::` example marker left as text.

It rebuilds every page each time, since Zensical's cache can serve a stale page and hide its
warnings. A link inside a docstring is not checked by the build; `tests/test_docs.py` checks
those. `scripts/check.sh full`, and so the pre-push hook, runs the script when one of the
site's sources changed, and CI's `site` job runs it on every pull request that changes one.

Zensical is young and releases about twice a week, and every build takes its newest release,
as every other dependency does. A release that breaks the build fails the `site` job, and with
it every pull request that changes a site source, `src/` included, until the build is fixed.

## Publishing to GitHub Pages

Publishing is off. The Docs site workflow, `.github/workflows/docs-site.yml`, builds and
deploys the site from every push to `main`, but its jobs run only when the repository variable
`PUBLISH_DOCS` is exactly `true`; otherwise they show as skipped. The published site is public,
so turn publishing on at the public launch, not before. To turn it on, in this order:

1. Under Settings, Pages, set **Source** to **GitHub Actions**. Without it, the deployment
   fails.
2. Flip the switch: under Settings, Secrets and variables, Actions, Variables, add the
   repository variable `PUBLISH_DOCS` with the value `true`.
3. Publish the current `main` at once: under Actions, Docs site, Run workflow, or

   ```bash
   gh workflow run docs-site.yml --ref main
   ```

From then on, every push to `main` republishes the site, so the site documents `main`, which
can be ahead of the latest release. The deploy job runs in the `github-pages` environment,
which GitHub creates for Pages.

A custom domain is optional: set it under Settings, Pages, and change `site_url` in
`zensical.toml` to match, since the built pages use it for their absolute links. To turn
publishing off, delete the variable; the site stays up until you unpublish it under Settings,
Pages.
