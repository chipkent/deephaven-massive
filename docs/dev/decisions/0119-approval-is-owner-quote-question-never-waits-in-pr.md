# 119. An approval is the owner's quote; a question never waits in a pull request

Date: 2026-11-15

Status: accepted

An approval of anything `AGENTS.md` reserves for the owner exists only as the owner's own words, verbatim and dated, from a message in the session or a decision file, together with the question those words answered when they are short. An author's claim ("owner-approved", "the owner decided"), a paraphrase, a brief, and a comment an agent posted under the owner's GitHub login claim nothing. A quote covers what its words name: it is never widened into a rule nor narrowed to the case asked. An owner ruling that sets, changes, or reverses a rule becomes a decision file in the next pull request on the subject, so the next agent finds it; a pull request that rewrites a rule in `AGENTS.md` says which decisions it touches.

A question for the owner goes to the owner directly, before the pull request opens, and never waits in a description, a review reply, or an issue. "Check before merging" lists only what the owner has settled, quoted, and the notices the description standard names. `scripts/check_pr_body.py` fails, locally before a push and in CI, on an item that asks the owner anything, on an approval claimed without the owner's dated quote, and on a rule change without its record.

The reason is one week of changes the owner never approved. Pull requests cited approvals no owner message contains, listed removals and public changes as "choices for the owner to confirm" and merged with them unconfirmed, rewrote an `AGENTS.md` rule on an owner yes that covered a different question, and extended code against rulings that lived only in chat. The owner, on 2026-11-15: "we have discovered many cases where you ran off and made major consequential changes without my approval. You need to assess the skills and AGENTS.md to make certain they are optimized to avoid these cases so that we don't have to keep reworking settled problems." On the proposed description check, the same day: "A PR description check is fine, but I hate using the ticketing system to keep track of what needs my feedback. You should be directly asking me. Having a description like this is just an indication that it is not yet ready to become a PR or for CI." On a proposed allow-list of root files, the same day: "You are back to an allow list, which has been extremely problematic thus far. It sounds like a bad plan. You've lost the high level common sense and replaced it with a broken rule." So the check judges the description and nothing else, and no file list is kept: the pre-push review starts from the diff's file list and asks whether every file serves the request.
